# 新系统接入指南（framework 通用内核）

> 适用版本：2026-11-23 企业级四项补齐（PyMySQL 数据通道 / 敏感信息脱敏 / API_ENV 多环境 / 结果沉淀）+ 场景编排层（framework.scenario，正向链路用例 YAML 化）之后。
> 本文档回答一个问题：**拿一个新系统接入本框架，需要准备什么、改哪里、怎么验收。**

---

## 1. 接入原理：你提供什么，框架提供什么

框架是「通用内核 + 业务项目」两层结构：

| 层 | 位置 | 接入新系统时 |
| --- | --- | --- |
| 通用内核 | `framework/`（请求、鉴权、断言、数据驱动、清理、报告、脚手架、DB、多环境） | **一行不动** |
| 业务项目 | `projects/<项目名>/` | 全部在这里新增 |

因此你要提供的**全部是被测系统的一手信息**，不是代码能力：

- 服务地址与测试账号；
- 鉴权方式的事实（登录路径、token 位置、携带方式）；
- 响应包装的结构（业务成功码、字段名）；
- 数据清理的途径（删除接口或数据库直连）；
- 接口清单、权限角色清单等用例材料。

---

## 2. 快速开始：三条命令

```bash
# 1. 生成项目骨架（项目名必须是合法 Python 标识符）
python -m framework.scaffold order_system --base-url http://127.0.0.1:9000 --prefix ORDER_

# 2. 复制 .env.example 为 .env，按 ORDER_ 前缀填配置（见第 4 节清单）

# 3. 跑生成的示例用例，验证链路
python -m pytest -o testpaths=projects/order_system/testcases
```

`--prefix` 默认为项目名大写 + `_`。前缀决定了该项目所有环境变量的命名空间，多项目可共存于同一份 `.env` 互不干扰。

## 3. 脚手架生成了什么

```text
projects/order_system/
├── __init__.py
├── config.py            项目配置：地址、鉴权 AuthSpec、账号、模块标签
├── conftest.py          fixtures：api / token(s) / cleaner / ctx / role_tokens / scenario_variables
├── helpers.py           数据构造助手（uid 随机串，按需扩展）
├── data/
│   ├── __init__.py      数据集入口：cases() / records() / load() / scenarios()
│   ├── api_cases.yaml   静态数据集 + permission_matrix + response_schemas
│   └── scenarios.yaml   场景编排：一个 YAML 块一条多步业务链路（见 6.5）
├── testcases/
│   ├── test_01_smoke.py        冒烟示例（可达性 / 登录后请求 / 路径无 5xx）
│   ├── test_02_permissions.py  权限矩阵示例（YAML 数据驱动）
│   ├── test_03_contract.py     响应契约示例（JSON Schema）
│   └── test_04_scenarios.py    场景编排通用入口（场景本体在 scenarios.yaml）
└── README.md            项目自述
```

生成的 9 条示例用例可被 pytest 直接收集，用于先验证「登录 → 带 token 请求 → 报告 → 清理」链路。
**注意**：模板里的 `/api/health`、`/api/auth/me`、`/api/products` 等是占位路径，铺真实用例前必须替换。

## 4. 信息收集清单（向被测系统确认的事实）

### 4.1 服务与账号 → `.env` + `config.py`

| 要提供 | 环境变量 / 位置 | 说明 |
| --- | --- | --- |
| 服务地址 | `<前缀>API_BASE_URL` | 生成时已随 `--base-url` 写入默认值，环境差异走 `.env` |
| 请求超时 | `<前缀>API_TIMEOUT` | 默认 10 秒 |
| 测试账号 | `<前缀>USERNAME` / `<前缀>PASSWORD` | 有几个角色给几组，命名可自定义 |
| 机器相关、无合理默认值的配置 | `CFG.require('键名')` | 只**登记**缺项、不在 import 期抛错；缺项由启动体检的「必填配置」一项统一报出（`API_CONFIG_STRICT=1` 可恢复立即报错） |

### 4.2 鉴权方式 → 只改 `.env` 的 `<前缀>AUTH_*`，零代码

| 向被测系统确认的问题 | 环境变量 | 默认值 |
| --- | --- | --- |
| 登录接口路径？ | `AUTH_LOGIN_PATH` | `/api/auth/login` |
| 登录体的用户名/密码字段名？ | `AUTH_USERNAME_FIELD` / `AUTH_PASSWORD_FIELD` | `username` / `password` |
| token 在登录响应的哪里？ | `AUTH_TOKEN_FIELD`（顶层字段名）或 `AUTH_TOKEN_PATH`（点分路径，如 `data.access_token`） | `token` |
| 怎么携带？ | `AUTH_MODE`：`bearer` / `header` / `cookie` / `auto` / `none` | `bearer` |
| 请求头名与前缀？ | `AUTH_HEADER` / `AUTH_SCHEME`（scheme 留空则原样发送） | `Authorization` / `Bearer` |
| Cookie 模式下关心的 cookie 名？ | `AUTH_COOKIE_NAME` | 空 |

要点：

- **不确定携带方式就用 `AUTH_MODE=auto`**：登录后能提取到 token 就走 header，否则有 Cookie 走 cookie；
- token 支持顶层与 `data` 层嵌套两种包装，`AUTH_TOKEN_PATH=data.access_token` 一类写法即可；
- 登录请求体需要额外字段时，在 `config.py` 的 `AuthSpec` 上加 `extra_login_body`；
- 登录失败会直接 `AssertionError` 并带完整响应，账号错误在第一轮就能暴露。

### 4.3 响应包装 → `config.py` 一处 +（必要时）conftest 的 Envelope

只需确认两个事实：

1. **业务成功码**是什么：200 / 0 / `"SUCCESS"`？ → `<前缀>SUCCESS_CODE`；
2. 响应顶层字段名是否就是 `code` / `message` / `data`？**是**则什么都不用改；**不是**（如 `{'meta': {'code': 0}, 'msg': ..., 'result': ...}`）在项目 conftest 的 `_client()` 里改映射：

```python
envelope=Envelope(code_key='meta.code', message_key='msg', data_key='result',
                  success_code=SUCCESS_CODE)
```

框架同时统计 HTTP 状态与业务 code 两层口径，负向用例主动触发的 4xx 不会污染通过率。

### 4.4 数据清理能力 → 二选一

用例产生的数据必须可回收，二选一（这是唯一可能要写业务代码的地方）：

| 途径 | 做法 | 提供什么 |
| --- | --- | --- |
| 被测系统有删除接口 | 用例里 `cleaner.register('动作名', lambda: api.delete(...))` 声明即可，框架统一执行、记录、写报告汇总 | 无（声明式） |
| 没有删除接口 | 业务层仿照 `projects/shopping/dbclean.py` 写精确 DELETE；连接复用、参数绑定、结构化结果由 `framework/db.py` 提供（PyMySQL） | `<前缀>MYSQL_HOST/PORT/DATABASE/USER/PASSWORD` |

清理特性（内核已内置）：目标已被用例删除按幂等成功处理；执行顺序可按依赖倒序注册；报告顶部展示「成功/跳过/失败」汇总；`CI=true` 或 `<前缀>DB_STRICT=1` 时数据库不可用直接失败，本地默认跳过落库断言。

**兜底 sweep（可选，推荐）**：注册式清理依赖每个用例主动 `register()`，中途异常或漏登记会留脏数据。新系统可在 `conftest.py` 的 `pytest_configure` 里补一段扫描器，框架在 session 收尾、所有 worker 结束后统一跑一次：

```python
from framework.cleanup import register_sweep

register_sweep(
    'API 测试用户',
    discover=lambda: dbclean.scan_test_keys('users'),  # 只读，返回残留标识
    clean=lambda key: dbclean.delete_test_keys('users', [key]),
    fallback='残留删除失败',
    prefixes=('API',),  # 内核二次校验：discover 扫宽了也删不到真实数据
)
```

要点：前缀必须是测试专用、不与真实数据相交；`discover` 只读且按前缀过滤；
兜底执行结果在报告与 `run_summary.json` 的 `cleanup` 字段里单列，数量 > 0 说明
有用例漏登记，应回头补 `cleaner.register()` 而不是长期依赖兜底。

> 场景编排用例（见 6.5）还有一种声明式清理：场景 YAML 的 `cleanup:` 列表，同样走删除接口、同样进报告汇总——被测系统有删除接口时，连清理动作都可以不写 Python。

### 4.5 权限矩阵角色清单（可选）

如果要做「角色 × 接口 × 期望结果」矩阵，需要提供：**角色名 → 账号**的映射。填进 conftest 的 `role_tokens` fixture（模板默认 `anonymous` / `user` / `admin` 三个键），矩阵行写在 YAML 的 `permission_matrix`，每行支持 `expect_http` / `expect_code` / `message_has` / `token_from`（跨用户凭证访问）。

### 4.6 运行环境

| 项 | 说明 |
| --- | --- |
| 被测服务可达 | 8080/9000 等按实际；冒烟第一步就是可达性检查 |
| MySQL 直连（仅 DB 清理方案需要） | 本机装 PyMySQL（`requirements.txt` 已含），无 mysql.exe 依赖 |
| Python | 3.10+，`pip install -r requirements.txt` |

| # | 位置 | 改什么 |
| --- | --- | --- |
| 1 | `projects/<项目名>/config.py` | 登录路径、账号、`SUCCESS_CODE`、模块标签 `MODULE_LABELS`、必要的 `CFG.require(...)` |

## 6. 用例编写规范与速查

### 6.1 命名与 marker

- 文件 `test_01_xxx.py` 按序号排列模块；marker 需在根 `pytest.ini` 的 `markers` 里登记后再用；
- 建议每个模块一个业务域，报告按 `MODULE_LABELS` 显示中文标签。

### 6.2 常用 API 速查

| 需求 | 写法 |
| --- | --- |
| 断言成功 / 业务码 / 消息 | `assert_ok(r)`、`assert_code(r, 400)`、`assert_message_contains(r, 'xx')` |
| 响应耗时预算 | `assert_elapsed(r, 800, '商品列表')`，预算 = 基准 × `API_SLA_SCALE`（默认 1.0），慢环境整体放宽而不改用例 |
| 一次核对多个字段（软断言） | `soft` fixture：`soft.equal(data['status'], 'SUCCESS', '订单状态')` … 末尾 `soft.assert_all()`，多条失败一次报全 |
| 接口覆盖率 | `data/api_inventory.yaml` 登记 method+path；conftest 里 `coverage.configure(path)`；跑完看 `reports/api_coverage.md`，CI 可用 `python -m framework.coverage --min 90` 做门禁 |
| 已知缺陷登记 | `@pytest.mark.xfail(strict=True, reason='...')` —— 缺陷修好后自动 XPASS 并被 strict 判失败，提示删标记 |
| 提取响应值（默认从 data 层） | `extract(r, 'data.list[0].id')`，支持数组下标与 `payload.` 显式切根 |
| 多值提取 | `extract_many(r, pid='data.id', name='data.name')` |
| 用例内依赖链 | `ctx.remember('id', r, 'data.id')` → `api.get(ctx.render('/api/x/${id}'))` |
| 构造 + 清理一次到位 | `cleaner.register('delete x', lambda: api.delete(...))` |
| 数据驱动 | `cases('数据集', '字段1', '字段2')`（tuple 列表）或 `records('数据集')`（dict 行） |
| 线性正向链路（能力储备） | `data/scenarios.yaml` 写场景 + 通用入口 `test_04_scenarios.py`，只写 YAML（见 6.5）；负向 / 落库 / 软断言 / 多身份写 Python |
| 落库断言 | 业务层 dbclean 查询函数（ shopping 的 `assert_order_persisted` 是范例） |

### 6.3 三条铁律（并行安全的前提）

1. **依赖链只在单个用例内闭环**：上游响应值传下游请求用局部变量或 `ctx`，绝不使用模块级全局变量或用例间依赖——否则无法单跑、无法 `-n 4` 并行；
2. **会写共享状态的数据要隔离**：后端按 user_id 存数据时（如购物车），每个用例注册独立用户（shopping 的 `register_isolated_user` 范式），用例结束由 cleaner 精确删除；
3. **清理幂等**：目标已不存在视为成功，登记 cleaner 要在拿到 ID 后立刻做，中途断言失败也不留脏数据。

> 6.5 的场景编排天然满足这三条：`ctx` 是 function 作用域、`${uid}` 每条场景唯一、cleanup 在场景开始即注册且幂等——只要给购物车类场景配好隔离用户的初始变量。
> 但要注意：引擎仅覆盖线性正向链路（能力储备），越权 / 强断言用例仍按本节铁律写 Python。

> **多身份注意（越权用例必读）**：`ApiClient` 内含一个 `requests.Session`，登录 / 注册返回的
> `Set-Cookie` 会一直带着。若被测服务 **Cookie 优先于 `Authorization` 头**（shopping 的
> `CookieUtil.token` 就是这样），同一个客户端先后登录两个账号会**静默串号**——请求头写着 A，
> 服务端按 Cookie 认成 B，断言看起来在测 A、实际请求的是 B。越权 / 会话隔离用例请每个身份
> 开一个客户端（shopping 的 `new_client` fixture），确实要复用时先调用 `clear_cookies()`。

### 6.4 数据驱动与契约

- **增删一行 YAML = 增减一条用例**；字段名必须完整覆盖 parametrize 参数名，缺字段在收集阶段即报错；
- 响应契约写在 YAML 的 `response_schemas`（JSON Schema Draft 7），`test_03_contract` 模板按 `response_schemas_cases` 逐条校验，失败信息精确到字段路径并附完整响应体。

### 6.5 场景编排：线性正向链路可只写 YAML（`data/scenarios.yaml`）

> **定位：能力储备，不是主流程默认写法。** 引擎只支持「请求 → 断言 → 提取 → 下一步」的
> 线性正向链路。负向 / 异常面（参数化非法值、鉴权异常、越权矩阵）、落库断言、软断言、
> 多身份 client 切换、条件分支 / 循环——这些请写 Python 用例，不要硬塞进 YAML。
> 判断口径：能「一条直线走到底且只看 HTTP/业务信封」的链路才适合 YAML。

线性正向链路（创建 → 审批 → 查询这类多步流程）不需要写 Python——一个 YAML 块一条场景，
`test_04_scenarios.py` 通用入口按场景名参数化执行，内核 `framework.scenario` 负责解释、
断言与清理：

```yaml
scenarios:
  - name: 下单支付
    vars: {order_name: 'SC-${uid}'}            # 场景级常量，可引用全局变量
    steps:
      - step: 创建订单
        request:
          method: POST
          path: /api/orders
          token: '${token}'                    # 缺省用客户端默认登录态
          body: {name: '${order_name}'}
        extract: {order_id: data.id}           # 步骤断言通过后提取变量
        assert: {ok: true, code: 200}          # 缺省 = {ok: true}
      - step: 支付
        request: {method: POST, path: '/api/orders/${order_id}/pay'}
    cleanup:                                   # 用例结束执行（步骤失败也执行）
      - method: DELETE
        path: '/api/orders/${order_id}'
        ignore_missing: true                   # 目标不存在视为成功
```

规则速查：

| 项 | 说明 |
| --- | --- |
| `steps[].request` | `{method, path, params, body, token, headers}`，值可含 `${变量}` |
| `steps[].extract` | `{变量: 提取路径}`，默认从业务 data 层提取，支持 `data.list[0].id` |
| `steps[].assert` | `{ok, http, code, message_has, schema, data_schema}`，缺省期望业务成功 |
| `cleanup[]` | 用例结束统一执行；`ignore_missing: true` 幂等；结果进报告清理汇总 |
| 变量来源 | conftest 的 `scenario_variables` fixture → 场景 `vars` → 步骤 `extract` |

防笔误：step/request/assert/cleanup 的**未知字段直接报错并列出合法键**，场景重名加载期报错；
失败信息带「场景名 · 第 N 步 · 步骤名」。shopping 的 `data/scenarios.yaml` 是完整范例
（审批入库链路 + 购物车链路）。

## 7. 运行、环境与 CI

```bash
python -m pytest                                   # 默认项目（pytest.ini 的 testpaths）
python -m pytest -n 4                              # 并行（框架已保证隔离）
python -m pytest -m smoke                          # 按标记过滤
python -m pytest -m scenario                       # 只跑 YAML 场景编排用例
set API_PROJECT=order_system && run.bat            # Windows 一键切项目
python -m pytest framework/tests -o addopts= -q    # 内核单测（不依赖任何后端）
```

**启动体检**：收集用例前先检查「服务可达 → 服务自检 → 数据库可用 → 登录可用」，任一必检项失败只输出一条 `ERROR: ...` 并以退出码 4 结束，用例零执行（不再出现「后端没起，上百条各报一次连接失败」）。`API_PREFLIGHT_ENABLED=0` 关闭，`API_PREFLIGHT_STRICT=0` 只告警不中止；`--collect-only` 不联网。新项目照抄 `projects/shopping/conftest.py` 的四项检查即可。

**多环境**：进程启动前设置 `API_ENV`（如 `set API_ENV=test`），框架先加载 `.env.test`（优先）再加载 `.env` 兜底，环境差异只维护差异项；`API_ENV` 会写入报告项目标签与 run_summary。

**报告产物**（`reports/`）：

| 产物 | 用途 |
| --- | --- |
| `report.html` | 单文件仪表盘报告：KPI、模块分布、TOP 接口、双层状态口径、请求明细（敏感字段已脱敏） |
| `archive/report_<时间戳>.html` | 历史归档，默认保留 30 份（`API_REPORT_KEEP` 可调） |
| `junit.xml` | CI 测试看板接入 |
| `run_summary.json` | 结果计数、环境、耗时，供趋势采集 |
| `failed_requests/` | 失败请求存档（含 trace_id 与重试次数） |

**CI**：复制 `.github/workflows/api-tests.yml` 调整 testpaths 即可；workflow 已含 ruff 门禁、内核单测、smoke/full 分层与产物上传；CI 环境自动启用 `DB_STRICT`。

## 8. 接入验收清单

按顺序勾完即可认为接入完成：

- [ ] `python -m pytest -o testpaths=projects/<项目>/testcases --collect-only` 收集无错（配置校验在这一步暴露）；

## 9. 已知边界与扩展点

| 边界 | 现状 | 扩展方式 |
| --- | --- | --- |
| 登录需要图形验证码 / 短信 | `AuthSpec` 不支持 | 扩展 `AuthSpec`（如自定义 login 回调），不改内核其他部分 |
| token 需要二次换取 / 多步交换 | `AUTH_TOKEN_PATH` 只处理一次登录 | 同上，项目层先调换取接口再注入 `default_token` |
| token 有效期长跑过期 | session 级登录一次 | 用例规模逼近有效期时再实现 401 自动重登 |
| 多身份共用一个客户端会串号 | 一个 `ApiClient` = 一个 `requests.Session`，Cookie 会累积 | 每身份独立客户端（shopping 的 `new_client`），或切换前 `clear_cookies()` |
| 接口覆盖靠手工清单 | `docs/接口清单.md` 式手工维护 | 接口数增长后考虑从 OpenAPI 生成覆盖矩阵 |
| 报告增强耦合 pytest-html 内部结构 | `requirements.txt` 锁版本 + 失败降级为原生报告 | 升级 pytest-html 时同步适配 `reporting/enhancer.py` |
| 负向用例的预期失败也进 `failed_requests/` | 存档有噪声 | 存档量大到影响排查时加 `expect_failure` 开关 |

## 10. 已知缺陷台账（可选，建议启用）

项目里出现 `xfail(strict=True)` 时，建议同时维护一份台账——否则 XPASS 让 CI 变红时
说不清是哪条缺陷，修复后也容易漏删标记。

1. 在项目的 `data/` 下建 `known_defects.yaml`，结构照
   `projects/shopping/data/known_defects.yaml`：每条缺陷一个 `DEF-xxx` 编号，
   绑定完整 pytest nodeid，状态 `open` / `fixed`；
2. 在项目 `conftest.py` 的 `pytest_configure` 中登记：

   ```python
   from framework import defects

   defects.configure(
       Path(__file__).parent / 'data' / 'known_defects.yaml',
       project='<项目名>',
   )
   ```

3. 每条 xfail 的 `reason` 以 `[DEF-001]` 这类编号开头，XPASS 时可直接反查；
4. CI 中加门禁（收集阶段即可校验，不必等用例执行）：

   ```bash
   python -m pytest --collect-only -q
   python -m framework.defects --ledger projects/<项目名>/data/known_defects.yaml \
     --project <项目名> --check
   ```

后端修复后必须**同时**删除 xfail 标记并把台账状态改为 `fixed`；
只做一半会被双向校验拦下。清单按项目名隔离，跑内核单测不会覆盖业务项目的收集结果。

## 11. 响应契约外置（可选，建议启用）

契约不写在用例或 `api_cases.yaml` 里，而是独立成 `data/contracts.yaml`，
服务方与消费方共用同一份文件。脚手架已生成样例（`contracts.yaml.tpl`），
不需要的项目删掉该文件与 `test_03_contract.py` 即可。

### 契约格式

```yaml
version: 1
project: <项目名>
contracts:
  health:
    method: GET
    path: /api/health
    token: null          # 仅说明角色，不参与校验
    response:            # JSON Schema Draft 7
      type: object
      required: [code, data]
      properties:
        code: {type: integer}
        data: {type: object}
```

加载时自检：version 必须为 1、contracts 非空、每条有 method/path/response、
schema 必须是合法 Draft 7。

### 两个方向

- **消费方**：`test_03_contract.py` 用 `framework.contract.assert_contract`
  按契约校验真实响应；建议再加一条测试，校验契约 method/path 已在接口清单登记。
- **提供方**：CI 用 `HEAD^` 的契约作基线跑 `framework.contract check`，
  删字段、改类型、加必填、收紧约束一律失败；新增可选字段、放宽约束放行。

```bash
python -m framework.contract validate --file projects/<项目名>/data/contracts.yaml
git show 'HEAD^:projects/<项目名>/data/contracts.yaml' > /tmp/baseline.yaml
python -m framework.contract check \
  --current projects/<项目名>/data/contracts.yaml --baseline /tmp/baseline.yaml
# 退出码：0 兼容 / 1 破坏性变更 / 2 文件错误
```

契约结构变了但服务方没同步时，CI 在这个步骤就红，不必等用例跑完。

### A.2 静态数据集（`data/api_cases.yaml`）与对应用例写法

```yaml
# ---- 负向：参数校验（纯标量集，cases 单字段返回标量列表）----
order_invalid_amounts:
  - amount: 0
  - amount: -1
  - amount: abc
  - amount: 99999999

# ---- 负向：创建订单的表单校验（patch 式，带期望消息）----
order_invalid_create:
  - patch: {items: []}
    message: 商品不能为空
  - patch: {addressId: 999999}
    message: 收货地址不存在
  - patch: {remark: "<script>alert(1)</script>"}
    message: 参数不合法

# ---- 状态机：合法状态值与业务含义 ----
order_status_values:
  - status: PENDING
    label: 待支付
  - status: PAID
    label: 已支付

# ---- 路径清单：未登录应被拒（method+path 整行，适合 records）----
endpoints_require_login:
  - method: get
    path: /api/orders
  - method: post
    path: /api/orders
  - method: delete
    path: /api/orders/1
```

对应用例（一个数据集 + 一行 parametrize = 一组用例）：

```python
# 单字段 → 标量列表：[0, -1, 'abc', 99999999]
@pytest.mark.order
@pytest.mark.parametrize('amount', cases('order_invalid_amounts', 'amount'))
def test_pay_rejects_invalid_amount(api, amount):
    result = api.post('/api/pay', json_body={'amount': amount})
    assert result.code == 400, (amount, result)

# 多字段 → tuple 列表；records → 整行 dict（字段多/可选字段时用）
@pytest.mark.order
@pytest.mark.parametrize('row', records('endpoints_require_login'),
                         ids=lambda r: '%s_%s' % (r['method'], r['path']))
def test_endpoints_require_login(api, row):
    result = api.request(row['method'].upper(), row['path'])
    assert result.code == 401, result
```

```python
# projects/order_system/config.py
ROLE_ACCOUNTS = {
    'buyer':  (CFG.get('BUYER_USER'),  CFG.get('BUYER_PASSWORD')),
    'seller': (CFG.get('SELLER_USER'), CFG.get('SELLER_PASSWORD')),
    'admin':  (CFG.get('ADMIN_USER'),  CFG.get('ADMIN_PASSWORD')),

```

**② conftest 的 `tokens` / `role_tokens` 按真实角色重写（替换模板默认的 user/admin 单账号）：**

```python
@pytest.fixture(scope='session')
def tokens():
    """各角色各登录一次；换账号只改 .env，用例零改动。"""
    result = {}
    for role, (user, pwd) in ROLE_ACCOUNTS.items():
        client = ApiClient(BASE_URL, TIMEOUT, auth=AUTH)
        client.login(user, pwd)
        result[role] = client.default_token
    return result


@pytest.fixture(scope='session')
def role_tokens(tokens):
    """权限矩阵的角色→token 映射；anonymous 是保留键，表示不带 token。"""
    return {'anonymous': None, 'buyer': tokens['buyer'],
            'seller': tokens['seller'], 'admin': tokens['admin']}
```

```yaml
permission_matrix:
```

### A.4 响应契约（`response_schemas` + `response_schemas_cases`）

```yaml
response_schemas:
  order_detail:
    type: object
    required: [code, message, data]
    properties:
      code: {type: integer, const: 200}
      message: {type: string}
      data:
        type: object
        required: [orderNo, status, amount, items]
        properties:
          orderNo: {type: string}
          status: {type: string, enum: [PENDING, PAID, SHIPPED, CANCELLED]}
          amount: {type: number, minimum: 0}
          items:
            type: array
            minItems: 1
            items:
              type: object
              required: [productId, quantity, price]
              properties:
                productId: {type: integer}
                quantity: {type: integer, minimum: 1}
                price: {type: number}

response_schemas_cases:
  - name: order_detail
    path: /api/orders/1001
```

- 模板的 `api` fixture 已带登录态（`default_token`），契约用例直接写路径即可；
- 失败输出定位到具体路径并附完整响应，例如 `data.items[0].quantity: 'abc' is not of type 'integer'`；
- **注意**：契约用例引用的资源 ID 要稳定存在（种子数据或先构造再校验），否则会误报 `data` 缺字段。
