## 1. 背景与目标

契约此前写在 `projects/shopping/data/api_cases.yaml` 的 `response_schemas` 段，只有消费方测试自己看得见。服务方改了字段，消费方只知道「测试红了」，不知道是否违反约定，也无法在合并前拦截。

本次把契约升级为**双方共用的可评审资产**，并补齐两个方向：

- **L1 契约外置**：结构定义从用例数据集中独立成 `contracts.yaml`；
- **L2 双向校验**：消费方运行时校验响应，提供方在 CI 对比基线拦截破坏性变更。

这是"多团队共享平台"演进三阶段（库化分发 → 契约外置 → 独立压测）的第二阶段，建立在已完成的库化分发（`cfe025f`）之上。

## 3. 核心设计

### 3.1 契约格式

```yaml
version: 1
project: shopping
contracts:
  health:
    method: GET              # 接口标识，便于服务方定位
    path: /api/health
    token: null              # 仅说明所需角色，不参与校验
    response:                # JSON Schema Draft 7，校验整个响应体
      type: object
      required: [code, data]
      properties:
        code: {type: integer}
        data: {type: object}
```

加载时自检：`version` 必须为 1、`contracts` 非空、每条必须有 `method` / `path` / `response`、`response` 必须是合法 Draft 7。错误直接报出契约名与字段，不会静默跳过。

### 3.2 内核 API

| 函数 | 职责 |
| --- | --- |
| `load_contracts(path)` | 加载并自检，返回契约映射 |
| `get_contract(contracts, name)` | 按名取契约，缺失时列出可用名称 |
| `assert_contract(result, contract, label='')` | 按契约校验响应，复用 `schema.assert_schema` 的字段路径定位 |
| `check_compatibility(baseline, current)` | 返回 `{ok, added, removed, issues, ...}` |
| `render_terminal(report)` | 终端/CI 日志输出 |
| `main(argv)` | CLI：`validate` / `check`，退出码 0 兼容 / 1 破坏 / 2 文件错误 |

### 3.3 破坏性变更判定

递归比对 JSON Schema，规则按"会不会让消费方出错"划分：

| 拦截（破坏性） | 放行（非破坏） |
| --- | --- |
| 删除字段、删除数组元素约束、删除整条契约 | 新增可选字段、新增契约 |
| 字段类型改变 | 移除必填约束 |
| 新增必填字段（`required` 增加） | `minimum` 变小 / `maximum` 变大等约束放宽 |
| `minimum` / `minLength` / `minItems` 变大；`maximum` / `maxLength` / `maxItems` 变小 | `enum` 扩大 |
| `const` 改变、`enum` 缩小、新增或改变 `pattern` | — |
| 新增 `additionalProperties: false` | — |

判定中修过两处自身缺陷：新增 `const` / `pattern` 约束原本漏判为破坏，已补进 `_compare()`。

## 4. 使用方式

### 4.1 消费方（运行时）

`test_14_contract.py` 按契约名参数化，从 `contracts.yaml` 取 method/path/token/response：

```python
CONTRACTS = load_contracts(CONTRACT_FILE)

@pytest.mark.contract
@pytest.mark.parametrize('name', ['health', 'categories', 'user_me', 'admin_stats'])
def test_response_schema(api, tokens, name):
    item = get_contract(CONTRACTS, name)
    role = item.get('token')
    result = api.get(item['path'], token=tokens.get(role) if role else None)
    assert result.ok, result
    assert_contract(result, item, label=name)
```

另有一条测试校验契约里的 method/path 已在 `api_inventory.yaml` 登记，避免契约与被测接口脱节。

### 4.2 提供方门禁（CI）

CI 步骤 `Contract compatibility (producer gate)` 在内核单测之后执行：

```bash
python -m framework.contract validate --file projects/shopping/data/contracts.yaml
if git cat-file -e 'HEAD^:projects/shopping/data/contracts.yaml' 2>/dev/null; then
  git show 'HEAD^:projects/shopping/data/contracts.yaml' > /tmp/contract_baseline.yaml
  python -m framework.contract check \
    --current projects/shopping/data/contracts.yaml \
    --baseline /tmp/contract_baseline.yaml | tee -a "$GITHUB_STEP_SUMMARY"
else
  echo "首次提交契约（HEAD^ 无基线），跳过兼容性对比"
fi
```

用 `set -o pipefail` 保证 `check` 的失败不会被 `tee` 吞掉。新项目照此改造即可。

### 4.3 本地验证

```bash
python -m framework.contract validate --file projects/shopping/data/contracts.yaml
python -m framework.contract check \
  --current projects/shopping/data/contracts.yaml \
  --baseline /tmp/baseline.yaml
```

## 5. 迁移说明

旧项目从 `api_cases.yaml` 迁移有三步：

1. 新建 `data/contracts.yaml`，把 `response_schemas` 里的每个 schema 放进 `contracts.<name>.response`；
2. 为每条契约补 `method` 与 `path`，按实际鉴权补 `token`；
3. 删除 `api_cases.yaml` 中的 `response_schemas` 与 `response_schemas_cases` 段，用例改用 `assert_contract`。

脚手架生成的新项目已经是全新格式，无需迁移。

## 7. 影响范围与兼容性

- **不破坏既有断言能力**：`framework.schema.assert_schema` / `assert_data_schema` 保持不变，契约校验只是复用它；场景引擎、软断言、覆盖率、台账均不受影响。
- **业务用例数 +1**：新增「契约接口已在清单登记」测试，178 → 179 条。
- **CI 多一步门禁**：放在内核单测之后、台账门禁之前，不依赖后端；破坏性变更会在用例运行前就失败。
- **契约是可选能力**：不需要契约校验的项目可删除 `contracts.yaml` 与 `test_03_contract.py`，内核其余功能不受影响。
