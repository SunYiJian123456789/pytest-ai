## 二、缺陷明细

### DEF-001 · 非 multipart 请求缺 file part 时返回 500

| 字段 | 值 |
| --- | --- |
| 状态 | open |
| 级别 / 责任侧 | medium / backend |
| 发现日期 | 2026-11-25 |
| 接口 | `POST /api/upload` |

**实测现象**：请求不带 multipart body 时，Spring 抛出 `MultipartException`，
项目没有 `@ControllerAdvice` 处理，直接回落到默认错误页——HTTP 500，
响应体没有 `code` / `message` 业务信封。

**预期行为**：缺少 file part 属于客户端请求错误，应返回 400 或 415，并带统一业务错误码。

**对应用例**：`projects/shopping/testcases/test_12_upload.py::test_upload_requires_file`

- 触发：`api.post('/api/upload')`，不带 `files` 参数；
- 断言：`result.ok is False` 且 `result.status in (400, 415)`；
- 实际命中 `result.status == 500` → 断言失败 → 被 `xfail(strict=True)` 登记；
- xfail reason 以 `[DEF-001]` 开头。

---

### DEF-002 · 上传文件超过 10MB 上限时返回 500

| 字段 | 值 |
| --- | --- |
| 状态 | open |
| 级别 / 责任侧 | medium / backend |
| 发现日期 | 2026-11-25 |
| 接口 | `POST /api/upload` |

**实测现象**：`application.yml` 配置了 `multipart.max-file-size=10MB`。
11MB、20MB 文件均触发 `MaxUploadSizeExceededException`，未处理直接回落 500 默认错误页，
无 `code` / `message`。

**预期行为**：超过上限应返回 `413 Payload Too Large`（或 400），并带业务错误码。

**对应用例**：`projects/shopping/testcases/test_12_upload.py::test_upload_rejects_oversize_file`

- 触发：1×1 透明 PNG 后拼 `11 * 1024 * 1024` 个空字节，以 `huge.png` / `image/png` 上传；
- 断言：`result.status in (400, 413)`；
- 实际返回 500 → 被 `xfail(strict=True)` 登记；
- xfail reason 以 `[DEF-002]` 开头。

---

### DEF-003 · 同一购物车并发支付产生多张成功订单（high）

| 字段 | 值 |
| --- | --- |
| 状态 | open |
| 级别 / 责任侧 | **high** / backend |
| 发现日期 | 2026-11-25 |
| 接口 | `POST /api/pay` |

**实测现象**：支付链路既没有幂等键也没有行锁。`PayController` 先查 `cartMapper.findByUser`，
再由 `PayService.record` 插单；多个请求同时读到非空购物车就会各自插入订单。
3 线程并发实测每轮都能生成 3 张 `SUCCESS` 订单，等价于重复扣款。

**预期行为**：同一购物车并发支付只应成功一单，其余返回「购物车为空」。

**对应用例**：`projects/shopping/testcases/test_17_idempotency.py::test_concurrent_payment_creates_single_order`

- 触发：3 线程 × 3 轮，用 `threading.Barrier` 让三个请求同时发出；每线程独立
  `new_client(token)`（后端 Cookie 优先于 Authorization，共用会话会串号）；
- 断言：每一轮 `result.ok` 的请求数必须恰好为 1；
- 实际每轮 3 单 → 被 `xfail(strict=True)` 登记；
- 多轮 + 栅栏是为了不让「刚好没撞上竞态窗口」把缺陷误判成已修复
  （strict xfail 的 XPASS 会让 CI 变红）；
- xfail reason 以 `[DEF-003]` 开头。

> 这是 5 条里唯一的高级别缺陷，涉及资金一致性，建议优先修。

---

### DEF-004 · 注册用户名超列宽触发 500

| 字段 | 值 |
| --- | --- |
| 状态 | open |
| 级别 / 责任侧 | medium / backend |
| 发现日期 | 2026-11-25 |
| 接口 | `POST /api/auth/register` |

**实测现象**：`sys_user.username` 是 `varchar(64)`，注册接口没有前置长度校验。
65 个字符起触发 SQL 数据过长异常，未处理回落 500 默认错误页。边界已实测确认：
64 字符成功、65 字符必 500。

**预期行为**：入库前校验长度，返回 400「用户名长度不合法」。

**对应用例**：`projects/shopping/testcases/test_20_input_bounds.py::test_register_rejects_oversize_username`

- 触发：`username = 'U' * 65`，`password = 'Test@123456'`；
- 断言：`result.status < 500` 且 `result.code == 400`；
- 实际返回 500 → 被 `xfail(strict=True)` 登记；
- xfail reason 以 `[DEF-004]` 开头。

---

### DEF-005 · 商品描述超 TEXT 容量触发 500

| 字段 | 值 |
| --- | --- |
| 状态 | open |
| 级别 / 责任侧 | medium / backend |
| 发现日期 | 2026-11-25 |
| 接口 | `POST /api/admin/products` |

**实测现象**：`description` 是 `TEXT`（65535 字节），商品描述没有长度校验。
25000 个汉字约 75000 字节直接撞库，未处理回落 500 默认错误页。

**预期行为**：入库前校验长度并返回 400。

**对应用例**：`projects/shopping/testcases/test_20_input_bounds.py::test_product_rejects_oversize_description`

- 触发：管理端提交商品，`description = '述' * 25000`（约 75000 字节），
  用例结束由 `cleaner` 审批/删除产生的商品；
- 断言：`result.status < 500` 且 `result.code == 400`；
- 实际返回 500 → 被 `xfail(strict=True)` 登记；
- xfail reason 以 `[DEF-005]` 开头。

## 四、维护流程与门禁

### 后端修复后要做两步（缺一不可）

1. 删除对应用例上的 `@pytest.mark.xfail(...)`；
2. 在 `known_defects.yaml` 里把该条 `status` 从 `open` 改为 `fixed`，
   并补 `fixed_date`。

### CI 会拦住只做一半的情况

| 场景 | 校验结论 |
| --- | --- |
| 台账 open，但用例已无 xfail | 提示改 `fixed`（疑似已修但没更新台账） |
| 台账 fixed，但用例仍有 xfail | 提示删标记（否则修复后 XPASS 让 CI 变红） |
| 用例有 xfail 但台账没登记 | 孤儿标记，报失败 |
| 台账 nodeid 没被收集到 | nodeid 拼错或用例已删，报失败 |
| xfail 非 strict / reason 缺 `DEF-xxx` | 报失败（XPASS 无法反查归属） |

本地复核命令：

```bash
python -m pytest --collect-only -q
python -m framework.defects \
  --ledger projects/shopping/data/known_defects.yaml \
  --project shopping --check
```

`--check` 退出码 0 表示台账与用例一致。每轮正常运行的 `reports/run_summary.json`
会写入 `known_defects` 统计，`reports/known_defects.md` 由台账自动渲染，
不需要手工维护第二份表格。

## 五、YAML 字段说明

| 字段 | 含义 |
| --- | --- |
| `id` | 缺陷编号，`DEF-001` 格式；必须出现在 xfail 的 `reason` 中 |
| `test` | 完整 pytest nodeid：`文件路径::用例名` |
| `status` | `open` = 缺陷存在且用例带 xfail；`fixed` = 已修复且用例无 xfail |
| `title` / `symptom` / `expected` | 标题 / 实测现象 / 正确行为（用例断言目标） |
| `endpoint` | 对应后端接口 |
| `severity` | `high` / `medium` / `low` |
| `discovered` | 发现日期 |
| `owner` | 责任侧：`backend` / `frontend` / `ops` |
| `fixed_date` | 修复日期，`status=fixed` 时填写 |
